# iOS 好友流量复测 · 2026-10-22

用户新增反馈：同一台 iPhone 关闭 Wi-Fi 后，Safari 能收到 `freekill-friends.pages.dev` 根路径的 JSON，中文乱码；游戏好友页仍显示连接失败。

这证明原域名的根路径在该次手机流量访问中可达，不再适合笼统描述为“iPhone 不能访问服务”。截图没有验证备用域名或 `/v1/state`，也不能证明带认证的 POST 登录和同步成功。用户随后确认：游戏截图也使用手机流量，但安装的是上一次版本，没有安装今天新增“聊天→角色”按钮的 IPA。因此这些截图不能作为 2026-10-22 新版失败的验证结果。

## 本轮已处理

原服务发出 UTF-8 JSON，但 `Content-Type` 只有 `application/json`。主、备用 Pages 代理现在为 JSON 明确追加 `charset=utf-8`；正文流不重新编码，原请求、HTTP 状态、缓存和限流头保留。两个代理仍通过 `FRIENDS_SERVICE` 绑定同一 Worker，未操作好友数据库或身份。

Node 回归覆盖 200、400、401、429、503 以及非 JSON 透传。线上主入口根路径仍为 404“接口不存在”，备用 `/v1/state` 仍为 401“好友服务登录已失效”，均带 UTF-8 编码标注。未登录收到这些业务响应属于预期，不代表浏览器无法联网。

## 请求对照与 iOS 兼容调整

本机同一网络中，Python 默认 User-Agent 得到 Cloudflare HTTP 403 / 1010；curl、Qt 6.8.3 的默认 XHR 和明确标注 `Xinyuesha-Test/0.5.25` 的请求均收到正常的匿名鉴权响应。这说明有客户端特征拦截，但**没有复现 iPhone 的具体失败**，不能把本机 Python 的结果直接等同于 iOS 根因。参考 [Cloudflare 1010](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1010/)。

iOS 好友 XHR 现在明确发送应用 User-Agent 和 Accept: application/json。非 JSON 的 HTTP 403 / 1010 显示拦截提示，其他 HTTP 错误显示状态码，无响应与超时分别保留明确提示；HTTP 200 却收到 HTML 不再当作认证成功。未改账号身份、密码派生、旧 token、备用切换范围，也不重放好友申请等写请求。设置标题含 `20261022.2`，用于核对实际安装版本。

局部回归覆盖 1010、503、异常 HTML、保留旧身份、HTTP 错误不重放及原有超时/备用/退出取消。Android 和 PC 分发文件保持上一轮版本；iOS 只更新受管资源，继续保留 f1ed000 原生修正。

乱码修正仍需该 iPhone 刷新确认，好友登录故障尚未解决。需要反馈者用流量、覆盖新版后再连接；成功前不把兼容调整标为真机修复完成。

## 20261022.3：区分服务地址与浏览器测试接口

用户已安装 20261022.2，并在流量下反馈：原入口显示两路均未收到 HTTP 响应；将备用 `/v1/state` 浏览器测试链接填入游戏后收到“接口不存在”。后者证明该次应用请求到达服务，但地址被当作服务根路径，旧逻辑会继续拼接 `/v1/register` 等路径并清除本地会话。它不能单独证明正确根地址的认证已成功，也不能把所有失败都归因于网络。

iOS 20261022.3 对两条已知入口的 `/v1/state` 测试链接自动整理为根地址，同一服务不清除好友身份和会话；已保存的错误测试地址在绑定游戏账号时自动修复。未知的内部路径在修改会话前拒绝，其他自定义服务仍保持隔离规则。设置显示实际使用的入口；连接时重新读取当前已登录游戏账号的本地配置，便于纠正错地址后恢复认证。

测试覆盖“输入测试链接保留身份、token 与零额外派生”“保存错误备用地址后直接恢复备用线路”“未知路径拒绝且不清会话”。保留 20261022.2 的请求标识和具体 HTTP 错误。正确的备用游戏服务地址为：

```text
https://xinyuesha-friends-api.pages.dev
```

末尾不带 `/v1/state`；该路径仅用于浏览器匿名连通测试。当前 20261022.2 用户也可先手动改为根地址并重新登录游戏验证，不必等待新包。20261022.3 的真实 iPhone 好友认证仍待反馈。
